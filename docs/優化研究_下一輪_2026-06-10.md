# 下一輪優化研究報告（2026-06-10）

> 方法：3 路並行深掃（LLM 管線延遲結構 / DmnAnalyzer 演算法 / TreeOptimizer 複製開銷），
> 全部讀碼驗證到 file:line。結論先講：**LLM 管線 ≫ DmnAnalyzer ＞ TreeOptimizer（不值得做）**。
> 使用者體感延遲幾乎 100% 在 LLM 串行呼叫上；引擎側演算法在現有資料規模下都是毫秒級。

---

## 一、LLM 管線（使用者體感延遲的全部 — 最高優先）

### 延遲解剖（實測自程式碼路徑）
`/generate` 最壞情況 **5-7 個「串行」LLM 呼叫**：

| 階段 | 呼叫數 | 位置 |
|------|--------|------|
| 初始生成 | 1 | `DecisionTableGenerator.doGenerateRuleJson` |
| JSON-parse retry | 最多 +3 | `ClaudeService.java:113-135`（`MAX_RETRY=3`，無 backoff，立即重打） |
| Self-repair | 最多 +3（tree）/+1（table） | `DecisionTreeGenerator`（`rules.tree.max-repair-rounds:3`） |

單呼叫 15-120s → 最壞情況 **5-9 分鐘**；典型（無重試）15-120s。
Grounding/Confidence 後處理為純 CPU（<10ms），不在關鍵路徑。

### 發現與干預（按 ROI 排序）

1. **JSON-parse retry 對語意錯誤無效卻佔最大延遲**（高影響/低工作量）
   解析失敗多半是 LLM 語意層問題，同 prompt 重試 3 次經常重複同樣錯誤，
   卻把延遲放大 4 倍。建議：`rules.llm.json-retry` 可配置、預設降為 1；
   語意錯誤交給 self-repair（它有錯誤回饋，重試才有資訊增量）。

2. **`/test-run` 是最危險的同步端點**（高影響/低工作量）
   `RuleService.testRun` 對每個 test case 逐一呼叫 `generate()`（`RuleService.java:317-375`），
   N 個 case = N×(15-120s) 串行 + 佔住 Tomcat worker。
   建議：套用 /generate 的 DeferredResult 模式 + case 間可平行（llmExecutor 已有容量）。

3. **同步 LLM 端點遷移**：`/explain`、`/narrate`、`/evaluate`（既有 backlog，壓測對照組已證明風險）。
   應抽共用 helper：`<T> DeferredResult<ResponseEntity<T>> asyncLlm(Supplier<T>)`，
   避免每端點複製 20 行樣板。

4. **快取覆蓋面太窄**：`@Cacheable("llmGenerate")` 只罩 Claude/Gemini 的初始生成；
   retry/repair/Ollama/OpenAI 都不快取。且 key 用 `description.hashCode()`（碰撞風險低但存在）。
   建議：cache key 改完整 hash；評估 repair 結果快取（同 envelope+issues → 同修復）。

5. **Offline-first（fast mode）**：現在固定先打 LLM、失敗才 fallback offline scenario。
   fast mode 反轉順序可讓預置情境 0.2s 回應。

6. **Repair prompt 帶整包 envelope（≤12000 字元）**：只送有錯的規則（delta）可省 50% input tokens。

7. **Provider retry 行為不一致**：Claude/Gemini 3 次、OpenAI 0 次、皆無 backoff —
   建議統一抽象到 LlmProvider 層 + 加 jitter backoff（API 限流時避免雪崩）。

## 二、DmnAnalyzer（演算法熱點 — 中優先，含一個正確性問題）

### 重要更正：「2^n 災難」其實有界
先前 backlog 寫「inclusion-exclusion O(2^n) 需改 Monte Carlo」— 深掃發現
**fallback 早已存在**（`DmnAnalyzer.java:555`：n≤20 走精確、>20 自動 Monte Carlo 50k 樣本，固定 seed 42）。
真正的問題比想像小，但仍有可做的：

1. **正確性問題：`expandCartesian` 靜默截斷**（`HyperRectangle.java:646`）
   IN 多值 × 多維笛卡爾積超過 1000 個超矩形時**靜默丟棄其餘**，
   overlap/gap 分析在截斷區域會漏報，且無任何警告。
   建議：超限時記 log + 在 `AnalysisResult` 加 `truncated: true` 欄位讓前端顯示「分析不完整」。
   這是**正確性透明度**問題，優先於任何效能項。

2. **n≤20 的 2^20 仍重**（最壞 ~1M 子集 × n × d）：閾值降到 ~15（2^15=32k）即可，
   Monte Carlo 50k 樣本的精度對 16-20 條規則足夠。一行改動。

3. **Overlap 粗篩**：`detectOverlaps`（`DmnAnalyzer.java:482-527`）是 O(n² × in² × d) 幾何交集。
   可用本輪做好的 `ConditionOverlapDetector` 掃描線當 pre-filter（已證實 185x），
   只對通過粗篩的對跑幾何交集。注意兩者語意不同（條件代數 vs 幾何），
   粗篩方向必須是「掃描線說互斥 ⇒ 幾何必不相交」— 成立（同一數值區間語意）。

4. **測試缺口**：DmnAnalyzer 與 HyperRectangle **沒有任何單元測試**
   （只有 TreeAnalyzerTest）。做任何上述改動前必須先補：
   inclusion-exclusion 對拍 Monte Carlo、expandCartesian 截斷行為、grid gap 偵測。

5. 平行化（overlap pairs / gap cells 天然獨立）→ 等前四項做完再評估，
   毫秒級工作量平行化收益有限。

## 三、TreeOptimizer（研究結論：不值得做）

深掃量化結果：典型樹 25 節點/深度 4，整條 6-pass 管線 **1-1.2ms**；
配置上限 depth=10 的最壞情況（~1000 節點）也只有 50-150ms，且跑在背景。
COW（copy-on-write）要追蹤修改路徑、與 4 個不變式測試互動，複雜度遠超收益。

**只值得做的兩個微項**（順手即可，不專門排程）：
- `TreeOptimizer.java:63-74` 兩次冗餘 `countNodes()`（每次 optimize 省 2 次遍歷）
- Pass 4 `canonicalHash` 用 `IdentityHashMap` memoize（大樹省 ~50% pass 4 時間）

先前 backlog 的「deepCopy 改 COW」項目**降級為不做**，理由：實測量級不構成瓶頸。

## 建議執行順序

| # | 項目 | 影響 | 工作量 | 性質 |
|---|------|------|--------|------|
| 1 | expandCartesian 截斷透明化 + DmnAnalyzer 補測試 | 正確性 | 0.5 天 | 修隱患 |
| 2 | /test-run 非同步化 + 共用 asyncLlm helper（含 /explain /narrate /evaluate） | 高 | 1 天 | 穩定性 |
| 3 | JSON retry 可配置（預設 1）+ offline-first fast mode | 高（體感延遲 -50~75%） | 0.5 天 | 延遲 |
| 4 | inclusion-exclusion 閾值 20→15 + overlap 掃描線粗篩 | 中 | 0.5 天 | 效能 |
| 5 | repair prompt delta 化 + 快取 key 強化 | 中（token 成本 -25~50%） | 1 天 | 成本 |
| — | TreeOptimizer COW | 低 | 高 | **不做** |

*所有效能項沿用本輪方法論：先 JMH/壓測固定基線 → 改 → 對比 → 全測試驗證。*
