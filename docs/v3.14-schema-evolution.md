## 1. 產品定位

**內部工具**，給集團壽險 BU 用。不對外、不商業化、不做與 DecisionRules / Rulebricks 的差異化定位。

| 維度 | 定位 |
|------|------|
| 客群 | 集團壽險核保 / 理賠 / 商品開發 / 法遵 / 精算 BA + IT 工程師 + 稽核 |
| 對標 | DR / RB / Camunda / IBM ODM 是**參考**，不是競爭對象 |
| 集團關係 | 金控集團 GAIA 2.0 是兄弟系統；本平台不取代「核保理賠智能工作臺」決策建議層，是規則治理層 |
| 邊界 | 規則**生成、查詢、解釋、稽核**前置服務；不執行規則（規則引擎是下游） |

如果它順手在「中文保險業 BA 規則治理」這個細分情境做得比通用平台好，那是 bonus，不是核心目標。

## 2. 核心命題與設計約束

### 2.1 核心命題

> **業務側（BA / 核保 / 理賠 / 法遵 / 精算 / 商品）與技術側（IT 工程師）能看同一條規則的不同層次，兩邊都看得懂，能同步修改、互不踩腳。**

### 2.2 設計約束（從 5/13 研究中得出的硬約束）

| # | 約束 | 為何 |
|---|------|-----|
| 1 | **單一事實來源**（一條規則一份檔案、不同層次讀） | BOM/XOM 雙模型 sync 業界 20 年驗證失敗：BA 永遠卡 IT 一拍 |
| 2 | **不寫死 template parser**（不能 parser-for-template-1 + parser-for-template-2） | 模板 #1 / #2 是示意，未來會擴充 |
| 3 | **AI 是草稿生成器 + 解釋器，不是仲裁者** | 金管會 2024 AI 指引「人類最終確認」、Camunda 自己也說 Copilot 不取代中間的人 |
| 4 | **雙人 review 不可省**（BA + IT 簽核） | LLM 翻譯 F1 0.7-0.85，且 HBR 2025/12 證實中英文推理會給不同答案 |
| 5 | **業務層敘述是規則第一身、技術層為延伸** | 金管會強制「人類可讀規則文件」、純工程化規則檔不能單獨存在 |
| 6 | **每條規則綁同一 ID，跨層用 metadata 連結** | 金管會稽核留痕要求 |
| 7 | **領域字彙表（glossary）是地基** | 中文場景必備；ODM verbalization 字典精神可借鏡 |

## 3. 5 層分層架構

```
┌──────────────────────────────────────────────────────────────┐
│ 一條規則 = 一份 RuleEnvelope JSON（唯一檔案、含所有層次）    │
└──────────────────────────────────────────────────────────────┘
       │
       ├─ L1【BA 摘要層】──────  自然中文敘述 +「條件 → 結果」一句話
       │                         （給 BA 寫 / 給稽核看 / 給法遵讀）
       │
       ├─ L2【業務語意層】──────  條件 / 檢核對 + 業務名詞（保額、通路…）
       │                         （給 BA 寫、給 IT 對照）
       │
       ├─ L3【規則結構層】──────  DecisionTable / Tree / Scorecard 表格
       │                         （兩邊都看、平台核心）
       │
       ├─ L4【執行表達層】──────  operator / typeRef / valueRef / scope
       │                         （給 IT 寫、給引擎執行）
       │
       └─ L5【整合對映層】──────  外部欄位代碼、code dict、API 對接
                                  （給 IT 寫 / 內部系統用）

  共用元件：
   • 領域字彙表（glossary）— 跨 L1-L5 綁定業務名詞 ↔ 技術欄位 ↔ 出處
   • Inline annotation — 每層可掛審查註解（BA / IT / 法遵）
   • Audit log — 誰改了哪層、何時、原因、審核狀態
```

### 3.1 每層的角色

| 層 | 主要讀者 | 內容 | 對應 v3.13 元件 |
|---|---|---|---|
| **L1** 敘述 | BA / 稽核 / 法遵 / 業務 | 中文一句話：「當 X 且 Y → 拋訊息 N.M」 | v3.12 BusinessNarrativeService（部分）|
| **L2** 語意 | BA / 法遵 + IT | 條件 / 檢核對、業務名詞、結構分節 | **缺**（v3.14 新增） |
| **L3** 結構 | 全員 | DecisionTable / Tree / Scorecard | ✅ RuleEnvelope.rule |
| **L4** 執行 | IT | operator / typeRef / valueRef / scope / hitPolicy | ✅ Condition / Result |
| **L5** 整合 | IT | externalCodes / fieldCode / unit / scale | ✅ FieldDef v3.12 既有 |

### 3.2 層之間的綁定

每條規則跨 5 層綁同一個 `ruleId`：
- L1 / L2 / L3 / L4 / L5 都引用相同 ruleId
- 領域字彙表的名詞被多層引用時，所有引用點都指向字彙表中**同一個 entry**
- annotation 也綁 ruleId + 層級 + 行號（類 GitHub PR line comment）

### 3.3 與經典架構的差異

| 經典 | v3.14 |
|------|-------|
| IBM ODM 用 BOM / XOM **雙模型**互相 sync | v3.14 用 **單檔多層**、不同視圖只是讀法不同 |
| Drools guided→DRL 單向、反向失敗 | v3.14 任一層改動，其他層 LLM 自動產草稿但**標「待 review」**，不直接寫入 |
| SBVR 純概念層、無執行 | v3.14 L1-L2 給 BA 看、L3-L5 給 IT，可執行性在 L3-L5 |
| DMN Level 1/2/3 同檔分層讀 | v3.14 **抄這個概念**，但分 5 層更細、且專為中文保險業 BA 設計 |

## 4. 領域字彙表（glossary）— 地基

### 4.1 為何字彙表是地基

中文保險業 BA 寫規則時，**業務名詞**是溝通的單位：保額、給付、等待期、責任準備金。若 BA 寫「保額」、IT 認為是 `sumInsured`、稽核以為是 `sumAssured`，三方對不上。字彙表把「業務名詞」當第一公民、所有層都引用它。

### 4.2 Entry Schema（每個名詞的欄位）

```yaml
term:
  zh_TW: "保額"
  zh_CN: "保额"
  en: "Sum Insured"
  synonyms: ["保險金額"]
  definition_business: "保險人最高給付額度"  # 一句話、BA 看
  examples:
    - "壽險主約保額 100 萬元"
  source:
    type: "law"           # law | guild_template | fsc | company_internal
    ref: "保險法 §72"
  technical_mapping:
    field_code: "SUM_INSURED"  # 內部系統欄位代碼
    data_type: "Money"         # Money | Enum | Date | Boolean | String | Integer | Decimal
    unit: "TWD"
    value_range: "[1, 100000000]"
  version: "1.0"
  status: "active"               # active | deprecated | proposed
  effective_from: "2026-05-13"
  deprecated_at: null
  related_terms: ["保費", "解約金"]
  regulatory_layer: "law"       # law | guild | fsc | company
  business_owner: "underwriting@grouplife"
  tech_owner: "platform-team@grouplife"
```

### 4.3 Starter 結構：~110 條，7 大分類

詳見 agent 研究結果（已可作為 starter v0.1）：

| 分類 | 條數 | 範例名詞 |
|------|----:|---------|
| 1. 核保 | 15 | 要保人 / 被保險人 / 受益人 / 保險年齡 / 等待期 / 既往症 / 標準體 / 加費 |
| 2. 商品 / 保單 | 14 | 保額 / 保費 / 保價金 / 責任準備金 / 解約金 / 滿期金 / 預定利率 / 宣告利率 |
| 3. 理賠 | 10 | 失能（殘廢）/ 失能等級 / 全殘 / 身故 / 重大疾病 / 特定傷病 |
| 4. 通路 / 銷售 | 8 | 業務員 / 保經 / 保代 / 行動投保 / 網路投保 / 受理編號 / 授權書編號 |
| 5. 繳費 | 10 | 寬限期 / 停效 / 復效 / 自動轉帳 / 指定帳戶轉帳 / A7 扣薪 / A8 扣薪 |
| 6. 法規 / 合規 | 10 | FATCA / CRS / AML / KYC / PEP / 受益所有人 / 制裁名單 |

**待 BU 確認項目**（agent 標「待確認」）：觀察期 vs 等待期區別、指定帳戶轉帳 / A7 / A8 扣薪、行動投保編號規則、預定費用率 / 解約率精算假設。

### 4.4 字彙表的關鍵壓測：殘廢 → 失能（2018-06-15）

人壽公會 2018 把「殘廢」改成「失能」，這條歷史變遷可當 schema 壓測：
- 舊規則用「殘廢」可以還原為 2018 之前版本
- 新規則用「失能」
- 用 `deprecated_at` / `version` / `effective_from` 三欄位完整重現切換日的 5 層分層快照

如果這條走不通，schema 還有結構問題。

### 4.5 擴展策略（agent 給的 5 步）

1. 挑 3 個 pilot 商品（1 利變終身 + 1 投資型 + 1 醫療附約）縱向打穿，補出 50-80 條公司特定名詞
2. 「殘廢 → 失能」變遷案例壓測
3. 接 lia-roc.org.tw / fsc.gov.tw 法規異動 RSS，新增 `proposed` 進待審佇列
4. 雙 owner 簽核流程（business + tech）
5. KPI：規則文件名詞覆蓋率 60%（上線）→ 85%（3 個月）→ 95%（半年）

## 5. 同步機制 — 單一事實，非雙向 sync

### 5.1 永遠以一份檔案為主

| 動作 | 主層 | 自動傳遞到 | 人工確認 |
|------|------|-----------|---------|
| BA 用模板寫一條規則 | L1 + L2 | LLM 草稿生 L3 / L4 | **IT review L4** |
| IT 改 operator / 加 valueRef | L4 | LLM 草稿生 L1 / L2 中文 | **BA review L2 文字** |
| 加新業務名詞 | 字彙表 | 所有 L1-L5 重新 lint | BA + IT 雙確認 |
| 改規則 | 任意層 | 其他層 LLM 同步 + 標記「待 review」 | 雙人簽核 |

### 5.2 關鍵原則

- LLM 跨層翻譯結果**一律標「待 review」**，**不直接寫入主檔**
- 雙人簽核（BA + IT）通過後才落地
- 對齊金管會「人類可讀 + 留痕」要求
- 對齊「Copilot 不取代中間的人」工業共識

## 6. 模板辨識策略

### 6.1 三方向研究結論

| 方向 | 評分 | 結論 |
|------|----:|-----|
| A. BPRF 純 LLM prompt（中文 326 條 benchmark）| 21/30 | F1 0.93 NER 但 schema 太扁、不支援 scope / 多錯訊 |
| B. Controlled NL（RuleCNL / SBVR-SE） | 13/30 | 中文 CNL 無前例、authoring 反人性、變體容忍度差 |
| **C. LLM + Structured Output + Few-shot** | **27/30** | **2024-2025 主流**、Anthropic Structured Outputs strict:true、彈性最強 |

### 6.2 推薦路線 D：混合方案

**C 為主幹 + A 的 prompt 策略 + B 的後段窄校驗**

| 步驟 | 內容 |
|------|------|
| 1. 抽取層（C） | Claude Opus 4.1 + Structured Outputs `strict:true`，schema = RuleEnvelope（scope / conditions / checks / messages 四節） |
| 2. Prompt 結構（A 的 pseudo-code grounding + DMN-Guided） | 分四階段呼叫：(a) 抽 scope、(b) 抽 conditions、(c) 抽 checks、(d) 綁訊息。模仿 DMN-Guided Prompting（arxiv 2505.11701）把 GPT-4o F1 從 0.53 拉到 **0.91** 的策略 |
| 3. 校驗層（B 退化版） | 不寫完整 CNL，只用 Lark 寫一個窄文法**驗證「條件表達式內部」**（欄位名 / 運算子 / 值），LLM 抽出 condition string 必須 parse 通過，否則 self-correction loop |
| 4. 語意層 | 欄位名對照字彙表（§4），未知欄位走 fuzzy match + 人工 review queue |

### 6.3 為何**不**寫死 parser

- 模板 #1 / #2 是示意、未來會擴充
- 寫死 parser 等於把「合理變體 + 新模板」當成 schema bug 而非 feature
- LLM + few-shot 加入新模板只要加 1-3 個 example，**零訓練成本**

### 6.4 量化測試方法（agent 提案）

| 元件 | 內容 |
|------|------|
| **Golden set** | 10-20 條規則，BA + 你共同標註 RuleEnvelope ground truth |
| **Perturbation set** | 5 軸變體 × golden set：句式 / 標點 / 結構 / 欄位 alias / 跨欄位 OR 密度 |
| **三層指標** | (1) Structural: JSON schema valid rate (應 100%) ／ (2) Field-level F1 (對齊 BPRF 0.934) ／ (3) Semantic equivalence（轉成 DecisionTable 跑 5-10 組 input 與 BA 預期比對） |
| **Production gate** | Field F1 ≥ 0.90 + Semantic equivalence ≥ 0.95；未達走人工 review |

## 7. UI/UX 推薦

### 7.1 主編輯區：Layered view（progressive disclosure）

- 預設展開 L1 + L2（給 BA 看）
- 按需展開 L3 / L4 / L5（給 IT 看）
- NN/G 研究：初始任務快 30-50%，保留 70-90% 進階能力可發現性
- 與 IBM ODM「Decision Center + Rule Designer」雙工具 toggle 模式相比，**不切換 UI** 是金融業 BA / IT / 稽核三方在同一條規則上協作的關鍵

### 7.2 註解區：Inline annotation（類 GitHub PR comments）

- 每層每行可釘中文註解
- BA 寫業務理由、IT 寫實作備註、法遵寫合規依據
- resolve / closed 狀態管理
- 留稽核軌跡（誰寫的、何時、針對哪一行）

### 7.3 AI 助手：右側 drawer 對話視窗

- 「解釋這條規則做什麼」
- 「補完這個 cell 的 FEEL 表達式」
- 「找所有與信用評分相關規則」
- 不取代主編輯區，只是輔助

### 7.4 字彙表瀏覽：左側 sidebar

- 點業務名詞跳到字彙表定義頁
- IDE outline + Wikipedia-style

### 7.5 不採用的模式

| 模式 | 為何不採 |
|------|---------|
| 純 Role-based UI | 跨角色協作硬傷、不適合 BA / IT / 稽核三方在同一條規則上對話 |
| Toggle 模式（IBM ODM 雙工具） | Eclipse 不友善、學習曲線陡、BA 切到技術視圖看不懂 |
| Split-pane（左右並排） | 螢幕寬度吃緊、雙方更新節奏不同會抖動 |

## 8. 中文 + 保險業特殊挑戰

| 挑戰 | 應對 |
|------|-----|
| **HBR 2025/12** 證實同 LLM 中英文推理會給不同答案 | LLM prompt 全程繁中、評測也用繁中 |
| 中文場景缺 benchmark | 用 BPRF（arXiv 2505.18542）中文 326 條 + INSEva 中文保險 LLM benchmark 對齊 |
| 保險術語高度領域化（責任準備金 / 等待期 / 除外責任） | 字彙表必須由 BU 提供初版、平台只負責維護結構 |
| 中文常「前提後置」（「滿 65 歲且投保滿 2 年者，…」） | DMN-Guided + pseudo-code grounding prompt 策略 |
| 同義詞歷史變遷（殘廢 → 失能） | 字彙表內顯式 version + deprecated_at + 法規依據 |
| 繁簡轉換 | 字彙表雙形對齊（內部用繁、對接 LLM 時轉繁） |
| 業務話術 ↔ 條款 ↔ 系統三層不一致（壽險占金融申訴 78%） | 每條規則綁「條款依據 / 商品送審文號」metadata |

## 12. 不在 v3.14 範圍（v3.15+）

| 項目 | 為何延後 |
|------|---------|
| DMN export | interop 訴求；非內部 BU 核心需求 |
| Rule Flow（多規則 DAG 編排）| Rulebricks 賣點；內部短期不需要 |
| Self-hosted / air-gapped | 金控集團部署策略決定，非平台層 |
| 跨主檔反查（HR 系統 lookup） | 介接複雜，先用 caller-pre-compute pattern 過渡 |
| Effective dating 在 lookup 路徑完整支援 | schema 已有、lookup 補上即可，獨立小工 |
| RAG over rules（語意搜尋） | 字彙表 + embedding 才能做，等 §10A 完成 |
| 跨 BU 多租戶（如未來擴銀行 BU） | 集團策略決定 |

## 13. 風險與緩解

| 風險 | 影響 | 緩解 |
|------|-----|-----|
| 字彙表 BU 不給初版 / 拖延 | A 階段卡住 | 平台先做 starter v0.1（agent 已給）、BU 校對；不能空手等 |
| LLM Field F1 達不到 0.90 | §6.2 模板辨識策略失敗 | 退到「人工 review queue + LLM 草稿」較保守模式；不上 production |
| BU 與「核保理賠智能工作臺」競合 | 內部資源分配 | 需求方 Q2 確認；定位差異（規則治理 vs 決策建議） |
| 5 層 schema 過度設計 | 維護複雜度 | 每層只在「有實際 use case 需要」時才開啟 column；NON_NULL 隱藏 |
| 雙人簽核流程 BA 嫌煩 | UX 阻力 | UI 設計上預設友善（一鍵 approve）+ 對 low-risk 規則可放寬 |
| 中文 LLM 在保險術語 hallucination | 規則品質 | 字彙表 lint + DMN-Guided four-stage prompt + 雙人 review 三道防線 |
