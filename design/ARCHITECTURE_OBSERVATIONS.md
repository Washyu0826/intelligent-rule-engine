## 1. How RuleService orchestrates today

`RuleService.generateFull(GenerateRequest)` is the single funnel that every `/tools/generate` and MCP `generate` call goes through, and its body literally numbers the nine steps in source comments. Step 1 (`resolveRuleType`) maps the request's `ruleType` string to the `RuleType` enum, defaulting to `DECISION_TABLE`. Step 2 looks up the matching `RuleGenerator` through `registry.getGenerator(type)` and throws `RuleGenerationException` if no Generator is registered. Step 3 calls `generator.generate(description, allowedFields, mode)` to produce a `JsonNode`, which is then converted to a `RuleEnvelope` via `objectMapper.treeToValue`. Step 4 backfills `schemaVersion` / `promptVersion` from `@Value` defaults. Step 5 performs the closed-loop validation by calling `doValidateEnvelope(envelope, type)` — if it reports errors, a warning string is appended to `envelope.reason` but generation still returns. Step 6 routes through one of two enrichers: `enrichWithTreeAnalysis` (for `DECISION_TREE`) or `enrichWithAnalysis` (DMN geometric, for everything else), each writing gaps/overlaps/simplifications/coverageRate into `envelope.evaluation`. Step 7 records an audit entry via `auditService.recordOperation` inside a try/catch tagged "non-fatal". Step 8 runs `groundingGuardService.check` to symbolically ground field and ENUM values back to the original description. Step 9 runs `confidenceScorer.score` to aggregate validation + grounding + analysis signals into a 0–100 tier. The whole flow returns a `GenerateResponse.builder()` carrying `envelope`, `validation`, `analysis`, `groundingCheck`, `confidence`, and `durationMs` — note that there is **no** `execution` field today, which is exactly the slot M7 will add behind the `executeAfterGenerate` flag.

## 2. How RuleTypeRegistry discovers generators / validators

`RuleTypeRegistry` is a single `@Component` whose constructor receives `List<RuleGenerator>` and `List<RuleValidator>` injected by Spring's collection injection — every `@Component` that implements either SPI is auto-collected, so adding a new generator/validator is purely a matter of dropping a Spring bean somewhere on the classpath. In `@PostConstruct init()` the registry iterates each bean, asks it for `supportedType()` (which returns a `RuleType` enum value), and puts it into an `EnumMap<RuleType, RuleGenerator>` (and a parallel `EnumMap<RuleType, RuleValidator>`). Lookup is `Optional`-returning: `getGenerator(type)` and `getValidator(type)` both return empty when nothing is registered, which is how `RuleService` produces the "型態 X 的 Generator 尚未註冊" error path. A type counts as "registered" only when **both** maps contain it — `getRegisteredTypes()` intersects the two keysets, and `isSupported(type)` AND-s the two `containsKey` checks. This matters because the adapter SPI in M2 will follow the same shape: a `List<RuleEngineAdapter>` injected into `AdapterRegistry`, with `@PostConstruct` building a `Map<String, RuleEngineAdapter>` keyed by engine name. The pattern is well-trodden here; do not invent a new discovery mechanism. Note also that `getTypeDescriptions()` is what feeds the MCP Resource view — any new adapter registry should expose an analogous read-only listing for the dashboard's adapter picker.

## 3. How EnvelopeNormalizer handles dirty LLM output

`EnvelopeNormalizer.normalize(envelope, schemaVersion, promptVersion)` is an in-place mutator that runs eight named passes after backfilling the two version strings and force-correcting `ruleType` to `"DecisionTable"` whenever the LLM emits something illegal (e.g. Ollama's habit of returning `"RuleEnvelope"`). The first pass, `normalizeHitPolicy`, upper-cases and trims the value and falls back to `"FIRST"` whenever it is not `"FIRST"` or `"MULTI"`. `ensureMutableLists` rebuilds every `inputs` / `outputs` / `rules` / `allowedValues` / `conditions` / `results` collection through `new ArrayList<>(...)` so that downstream passes can mutate them without hitting `UnsupportedOperationException` from `List.of()` literals. `normalizeTypeRefs` rewrites alias shorthand through `normalizeTypeRef`: `INT|LONG|NUMBER → INTEGER`, `BOOL → BOOLEAN`, `STR|TEXT|VARCHAR → STRING`, `LOCALDATE|DATETIME → DATE`, etc. (no entry for `TIMESTAMP` or `VARIABLE` today — see risk register). `autoInferEnumAllowedValues` scans the rule rows to recover `allowedValues` for any ENUM field where the LLM forgot to declare them, accepting `equals`, `notEquals`, and `in` conditions. `normalizeRuleIds` assigns `R01..Rnn` and `priority = i+1` to any row missing those fields. `normalizeOperatorsAndValues` is the largest pass: it drops empty conditions, runs `normalizeOperator` (e.g. `eq → equals`, `gt → greaterThan`, `oneof → in`, `range → between`), calls `unwrapNestedValue` to peel off the LLM-wrapped envelopes `{"type":"integer","value":60}`, `{"enum":"reject"}`, `{"value": X}`, `{"allowedValues":[...]}`, and the two-key `{typeRef, X}` shape — recursively. It then runs `repairBooleanValue` (mapping `"true"`, `"yes"`, 是, 有 to `true`; `"false"`, `"no"`, 否, 無, 沒有 to `false`) and `repairNumericValue` (string-to-`Long`/`Double` for INTEGER/DECIMAL columns, including elements inside a `between` array). Finally `deduplicateRules` removes rows whose `(conditions, results)` fingerprint repeats and `sortByPriority` orders by `priority`. The pass list is fixed; there is no extension hook today, which is the operative concern for M3.

## 4. How validation layering works

`DecisionTableValidator` (the `RuleValidator` for `RuleType.DECISION_TABLE`) holds a `List<ValidationLayer>` injected by Spring — the four implementations carry `@Order(1)` through `@Order(4)` so Spring delivers them in deterministic order. `validate(JsonNode envelope)` creates one fresh `ValidationContext` (a `@Data` object holding `ruleNode`, `hitPolicy`, `inputTypes` / `inputAllowed`, `outputTypes` / `outputAllowed`, `parsedRules`, `referencedInputs`, and a `shouldContinue` boolean defaulting to `true`), then loops the layers, accumulating errors and breaking early whenever a layer flips `context.setShouldContinue(false)`. Layer 1, `StructureValidator`, checks that `ruleType`, `rule`, `hitPolicy`, `inputs`, `outputs`, `rules` exist, emits `MISSING_FIELD` / `TYPE_MISMATCH` / `INCONSISTENT_TABLE` codes, parks `ruleNode` and `hitPolicy` on the context, and sets `shouldContinue=false` if any structural prerequisite is missing. Layer 2, `FieldDefinitionValidator`, parses each `FieldDef` and populates `inputTypes` / `inputAllowed` / `outputTypes` / `outputAllowed`, emitting `DUPLICATE_ID`, `MISSING_FIELD`, `TYPE_MISMATCH` (against `TypeRefs.ALL`), `ENUM_VALUE_MISSING`, and an `INCONSISTENT_TABLE` for input/output name collisions. Layer 3, `RuleSemanticValidator`, walks each rule row to emit `MISSING_FIELD`, `DUPLICATE_ID`, `UNKNOWN_FIELD`, `UNKNOWN_OPERATOR`, `TYPE_MISMATCH`, `INVALID_ENUM_VALUE`, `MISSING_RESULTS`, while populating `parsedRules` (a list of `ParsedRule(ruleId, Map<field,ConditionInfo>)`) and `referencedInputs`. Layer 4, `ConsistencyValidator`, consumes the parsed state to emit `INCONSISTENT_TABLE` warnings for unreferenced inputs and `INVALID_MULTI` for FIRST-conflicting rule overlaps, delegating geometric work to `ConditionOverlapDetector`. The short-circuit is one-way (a later layer never re-enables it), and each layer's `validate` method is purely additive — `context.errors` does not exist, errors flow through return values. This means M3's new error codes (for `extensions{}`) must live either inside an existing layer (likely Layer 3 for field-OR semantics, Layer 1 for malformed `extensions` block) or as a new `@Order(5)` layer; the registry pattern allows the latter without touching `DecisionTableValidator`.

## 5. Proposed location for `service/adapter/` and `service/engine/`

### 5.1 `service/adapter/`

- **Proposed full package path:** `com.ruleengine.rules.service.adapter` and `com.ruleengine.rules.service.adapter.group`. Matches `PROJECT_PLAN.md` Appendix §B and `MISSION.md` §2.2 verbatim.
- **Contents created in M2:** `RuleEngineAdapter.java` (SPI interface), `AdapterRegistry.java` (Spring auto-discovery via constructor-injected `List<RuleEngineAdapter>` + `@PostConstruct`, mirroring `RuleTypeRegistry`), `group/GroupAdapter.java` (NotImplementedException stub).
- **Contents created in M4/M5:** `group/GroupJsonExporter.java`, `group/GroupJsonImporter.java`, `group/GroupXlsxExporter.java`, `group/GroupCodeTable.java`, `group/GroupLayoutEngine.java`.
- **Relationship to `service/exporter/` stub:** The existing `service/exporter/InternalEngineExporter` is **not** absorbed by `GroupAdapter`. Three reasons. (a) `RuleExporter` (the existing SPI) returns a single `ExportResult(engineName, engineVersion, format, content, warnings, metadata)` record carrying a serialised string and a pre-flight warning list — that is a "deployment-package builder" contract, not a "bidirectional converter" contract. `GroupAdapter` must additionally support `RuleEnvelope ← Group JSON` (the importer side) and `RuleEnvelope → xlsx` (a binary stream) — neither fits inside `ExportResult.content : String`. (b) `MISSION.md` §2.3 explicitly states "*The contents of `service/exporter/` are not to be removed. The stub remains so that any caller depending on its presence keeps working*" — at least one caller is a Spring bean wired by other code (it is `@Component`), and `RuleService`/dashboard call sites may reference it directly; removing it is a backward-compatibility break we cannot justify. (c) The two SPIs target different lifecycle stages: `RuleExporter.export()` is a one-shot deployment-package emitter that flags missing `fieldCode` / `externalCodes` / `effectiveDate` (i.e. governance pre-flight), while `RuleEngineAdapter` is a runtime conversion layer feeding `MockGroupEngine`. Coexistence is the correct posture: `InternalEngineExporter` keeps producing its placeholder JSON wrapper for the existing dashboard "deployment view"; `GroupAdapter` produces the live Group tree JSON for the new "Engine Execution" tab.
- **Read-only dependencies:** `com.ruleengine.rules.domain.envelope.*` (RuleEnvelope and inner types), `com.ruleengine.rules.domain.RuleEnvelopeExtensions` (after M3 lands), `com.ruleengine.rules.domain.RuleType`. May read `service/validator/*` for pre-flight checks but **must not** invoke or modify validators (validation is owned by `RuleService.doValidate*`).
- **Must not touch:** `service/RuleService.java` (only M7 touches it, additively); `registry/RuleTypeRegistry.java`; `service/generator/*`; `service/validator/*`; `service/exporter/*`; `controller/*` (M7 only).
- **Style adherence (`MISSION.md` §2.4):** Lombok `@RequiredArgsConstructor` + `@Slf4j` (matches `RuleService`, `InternalEngineExporter`); constructor injection for collaborators; `@JsonInclude(NON_NULL)` on any DTO emitted by importer (matches `RuleEnvelope` and `RuleEnvelopeExtensions`); JUnit 5 patterns for the interface-level discoverability test in M2.

### 5.2 `service/engine/`

- **Proposed full package path:** `com.ruleengine.rules.service.engine`. Matches `PROJECT_PLAN.md` Appendix §B.
- **Contents created in M6:** `RuleEngineRunner.java` (`evaluate(tree, input) -> ExecutionResult` interface), `MockGroupEngine.java` (default `@Component` implementation), `ExecutionResult.java` (typed record carrying hit path, hit leaf, returned values, or a structured no-hit outcome).
- **Relationship to `service/exporter/` stub:** None, directly. The engine package consumes the output of `GroupAdapter` (Group tree JSON), not of `InternalEngineExporter`. The exporter remains a governance/deployment artefact emitter; the engine package is a runtime evaluator. They are orthogonal and `InternalEngineExporter` should not be edited to bridge them — M7's `RuleService.generateFull` branch is the integration point.
- **Read-only dependencies:** `com.fasterxml.jackson.databind.JsonNode` (for the tree), a `Map<String, Object>` input record. Crucially, per `MISSION.md` §6 (M6 acceptance), the public `evaluate` signature **must not** leak Group-specific types — `GroupCodeTable` lives inside `service/adapter/group/` and is consulted internally by `MockGroupEngine`, not exposed on the interface.
- **Must not touch:** `service/adapter/group/GroupJsonExporter.java` cyclically (engine consumes its output, no reverse dependency); `domain/*` modifications; `service/validator/*`.
- **Style adherence (`MISSION.md` §2.4):** Lombok where the surrounding code uses it; constructor injection if Spring beans are needed (likely just `MockGroupEngine` itself); `ExecutionResult` as an immutable Java `record` (matches `RuleExporter.ExportResult`); `@JsonInclude(NON_NULL)` on serialised result fields so the absence of `hitLeaf` does not pollute API responses.

## 6. Risk register

| # | Risk | Why-now | Mitigation |
|---|---|---|---|
| 1 | `EnvelopeNormalizer.normalizeTypeRef` rewrites `LOCALDATE` / `DATETIME` to `DATE` and has no branch for `TIMESTAMP` or `VARIABLE`; LLM-emitted `TIMESTAMP` strings will fall through `default -> upper` and reach `FieldDefinitionValidator.parseFieldDefs`, which rejects them with `TYPE_MISMATCH` against `TypeRefs.ALL` (today: INTEGER / DECIMAL / BOOLEAN / STRING / ENUM / DATE). | M3's plan adds `TIMESTAMP` and `VARIABLE` at the tail of the typeRef enum, but if `TypeRefs.ALL` is not updated in lockstep every envelope using the new types fails Layer 2. | M3 impl-worker must extend `TypeRefs.ALL`, add a `normalizeTypeRef` case for common synonyms (`TS`, `INSTANT`, `VAR`), and add a unit test that round-trips a `TIMESTAMP` typeRef through `EnvelopeNormalizer` and `FieldDefinitionValidator` without errors. |
| 2 | `EnvelopeNormalizer.unwrapNestedValue` recursively peels `{"value": X}` / `{"enum": X}` / single-key maps; an `extensions.globalGuard[].value` shaped as `{"type":"TIMESTAMP","value":"2026-01-01T00:00:00Z"}` would be unwrapped to a bare string, but a *nested* `{ field: {ref: "<被保人生日>"} }` envelope used inside `extensions.fieldOr` may collide with the single-key-map heuristic at `EnvelopeNormalizer.java:395` and silently flatten away the structure. | The normaliser was designed for `Condition.value` only; it has never been called on extension payloads. | M3 architect-worker must declare which paths inside `extensions{}` are subject to value normalisation; M3 impl-worker should add a dedicated `normalizeExtensions(rule)` pass that explicitly walks `globalGuard` / `fieldOr` / `groupings` / `footnotes` and only re-uses `unwrapNestedValue` on `Condition.value` and `Condition.valueRef`, not on the structural keys. |
| 3 | Existing test suite (~37 test files under `src/test/java/com/ruleengine/rules/`, slated as "~75 test classes" in `PROJECT_PLAN.md` §8 success criterion 6) was written against the pre-`extensions` envelope and against the eight-pass normaliser ordering; adding a ninth pass in `EnvelopeNormalizer.normalize` or a fifth `@Order(5)` layer in `DecisionTableValidator` can change error code ordering or attach unexpected warnings to `envelope.reason`, breaking string-matching assertions. | Several existing tests assert on `validation.getErrors().get(0)` and on substrings of `envelope.reason` (see `RuleService.generateFull` line 113 "（⚠ 自動驗證發現 %d 個問題」). | Before M3 impl, the test-worker should snapshot the current error-code ordering for the 12 built-in samples; M3 impl-worker must keep all new normalisation passes idempotent on envelopes with no `extensions` block and gate any `envelope.reason` mutation on `extensions != null`. | 5 | `RuleService.generateFull` returns a `GenerateResponse` whose builder fields are fixed (envelope / validation / analysis / groundingCheck / confidence / durationMs); M7's `execution` block must be added without changing field ordering or making any existing field nullable in a way that breaks Jackson on consumers that pinned schema. | The dashboard's TypeScript types and the MCP `RulesMcpToolService` (11 `@Tool` methods, per `MISSION.md` §2.1) deserialise this DTO; reordering builder fields or renaming any of the five existing fields is a backward-compat break. | M7 architect-worker must specify `execution` as an additive `@JsonInclude(NON_NULL)` field appended at the bottom of `GenerateResponse`; smoke test must assert that with `executeAfterGenerate=false` the serialised JSON is byte-equivalent to today's output. |
| 6 | `service/exporter/InternalEngineExporter` is `@Component` and so is auto-wired; if M4 introduces a `GroupAdapter` that also publishes `engineName = "group-internal-engine"`, both beans could end up routing to the same dashboard slot and confuse the existing "deployment view" callers. | The exporter declares `ENGINE_NAME = "group-internal-engine"` (constant string in `InternalEngineExporter.java:39`); a naïve `GroupAdapter.engineName()` returning the same string would collide in the new `AdapterRegistry` namespace and in any UI dropdown that merges adapters with exporters. | M2 architect-worker must namespace the new SPI: `GroupAdapter.engineName()` returns `"group-group-engine"` (distinct from the exporter's `"group-internal-engine"`); `AdapterRegistry` and the existing `RuleExporter` discovery must remain in separate Spring bean maps; the dashboard's adapter picker reads only from `AdapterRegistry`, never merges the two. |
